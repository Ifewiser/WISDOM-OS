# WISDOM OS — Phase 6D-A: Local → Cloud Migration Readiness Audit

We are preparing to migrate the existing WISDOM OS browser-local data layer to the already-configured Supabase/Postgres backend.

Phase 6C.5 is COMPLETE and CLOSED.

The live Supabase environment has already been verified with two authenticated test users. Authentication, workspace bootstrap, RLS, workspace isolation, ownership protection, membership protection, composite foreign keys, daily-plan privacy, focus-session privacy, and migration reproducibility have all passed.

Do NOT implement the migration yet.

Do NOT add migration code.

# 4. DAILY PLAN MIGRATION

This requires special attention.

The local model currently represents daily planning using fields such as:

* bigRockTaskId
* supportTaskIds
* adminTaskIds

The cloud model uses:

* daily_plans
* daily_plan_items

Inspect the actual implementation and determine exactly how every local daily plan should become:

1. one cloud `daily_plans` row
2. zero or more `daily_plan_items` rows

Map:

* Big Rock → role
* Support → role
* Admin → role
* ordering/position
* task relationship
* plan date
* planningCompleted
* timestamps

Determine what should happen if:

* a referenced task no longer exists
* the same task appears more than once
* an ID is null
* arrays are empty
* a task appears in multiple roles
* a plan references a task belonging to another local workspace
* malformed local data exists

Do not fix anything yet. Just report the required migration behavior.

# 5. TASK PRIORITY VS DAILY PLAN ROLE

The cloud architecture intentionally keeps:

* Task priority as current task state
* Daily plan item role as historical plan membership

Audit whether the current local implementation duplicates these concepts.

Determine whether the migration should preserve:

* task.priority
* daily_plan_items.role

independently.

Identify any inconsistencies that may already exist locally, for example:

* a task marked BIG_ROCK but appearing as SUPPORT in a historical plan
* a task marked SUPPORT but not appearing in today's plan
* multiple planned tasks with the same priority
* tasks appearing in plans but currently having priority NONE

Do not normalize or silently change these values during migration.

Report how they should be preserved.
