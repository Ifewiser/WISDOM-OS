## Verify 1: Supabase auth.users references

Inspect every foreign key referencing auth.users.

Confirm:

* They reference exactly auth.users(id)
* auth.users is never recreated
* no migration attempts to CREATE TABLE auth.users
* no application migration attempts to modify Supabase's managed auth schema

Report every auth.users foreign key found.

## Verify 2: Composite workspace foreign keys

Inspect the actual SQL/schema definitions.

Verify:

tasks:
(workspace_id, category_id)
→ categories(workspace_id, id)

tasks:
(workspace_id, project_id)
→ projects(workspace_id, id)

daily_plan_items:
(workspace_id, daily_plan_id)
→ daily_plans(workspace_id, id)

daily_plan_items:
(workspace_id, task_id)
→ tasks(workspace_id, id)

focus_sessions:
(workspace_id, task_id)
→ tasks(workspace_id, id)

Confirm that the required unique constraints exist on referenced columns so PostgreSQL accepts these composite foreign keys.

Flag any relationship that is only application-level rather than database-enforced.

## Verify 3: Delete behavior

Inspect ON DELETE behavior for every foreign key.

Confirm:

* deleting a workspace can cascade its owned data
* deleting a workspace member does NOT delete the workspace
* deleting a category does not unexpectedly delete tasks
* deleting a project does not unexpectedly delete tasks
* deleting a task does not silently destroy historical plan/session data unless explicitly intended
* daily_plan_items are removed when their daily_plan is removed

Report any potentially dangerous cascade.

Focus sessions:

Report any constraint that is missing or weaker than intended.
