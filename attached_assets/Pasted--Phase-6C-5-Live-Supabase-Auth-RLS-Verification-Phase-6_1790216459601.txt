`lib/db/drizzle/0002_phase_6c_auth_rls.sql`

### 2. Verify database objects

Confirm the live database contains:

* profiles
* workspaces
* workspace_members
* categories
* projects
* tasks
* daily_plans
* daily_plan_items
* focus_sessions

Verify:

* RLS is enabled on all nine tables.

* `public.is_workspace_member(uuid)` exists.
* `public.bootstrap_user_workspace(text,text)` exists.
* The bootstrap function is executable by `authenticated`.
* It is NOT executable by `anon` or `public`.
* No service-role credential is exposed to browser code.

Do not weaken any RLS policy merely to make a test pass.

### 4. Live workspace isolation test

Create identifiable test data:

User A:

* Workspace A
* Category A
* Project A
* Task A
* Daily Plan A
* Focus Session A

User B:

* Workspace B
* Category B
* Project B
* Task B
* Daily Plan B
* Focus Session B

Then test the actual Supabase client/database behavior.

#### User A must NOT be able to:

* SELECT Workspace B
* SELECT User B's membership
* SELECT Category B
* SELECT Project B
* SELECT Task B
* SELECT User B's daily plan
* SELECT User B's daily-plan items
* SELECT User B's focus session

Also attempt:

* INSERT a task into Workspace B
* UPDATE Task B
* INSERT a project into Workspace B
* UPDATE Project B
* INSERT a category into Workspace B
* UPDATE Category B
* INSERT/update daily-plan data belonging to User B
* INSERT/update a focus session belonging to User B

All unauthorized operations must fail or return zero rows according to the policy behavior.

Repeat the same isolation tests in the opposite direction for User B against User A.

### 5. Membership escalation tests

Explicitly test that a normal authenticated browser client cannot:

* INSERT itself into an arbitrary workspace through `workspace_members`
* Change its membership role to owner/admin
* Modify another user's membership
* Delete another user's membership
* Change `workspaces.created_by`
* Change `tasks.created_by`

Test both users.

### 6. Bootstrap RPC security tests

Test the RPC from an authenticated client:

* User A can bootstrap its own workspace.
* User B can bootstrap its own workspace.
* Repeated bootstrap calls are idempotent.
* User A cannot cause a workspace to be created for User B.
* The RPC cannot be called by an unauthenticated client.
* The RPC cannot be used to create arbitrary workspace memberships.

Also inspect the function definition and confirm the `SECURITY DEFINER` function has a locked `search_path` as intended.

### 7. Cross-workspace foreign-key tests

Attempt to create:

* Task in Workspace A referencing Category B.
* Task in Workspace A referencing Project B.
* Daily-plan item in Workspace A referencing a plan/task from Workspace B.
* Focus session in Workspace A referencing Task B.

These must fail because of the workspace-safe composite foreign keys, even independently of RLS.

### 8. Personal-data isolation

Verify specifically that:

* User A cannot read User B's daily plans.
* User A cannot modify User B's daily plans.
* User A cannot read User B's focus sessions.
* User A cannot modify User B's focus sessions.

Workspace membership alone must not grant access to another user's personal daily-plan/focus data.

### 9. Verify browser security

Inspect the built/browser-facing application and confirm:

* Only `VITE_SUPABASE_URL` and the public publishable/anon key are present.
* No service-role key exists in browser code.
* No database password exists in browser code.
* No privileged Supabase credential is embedded in the frontend bundle.
* No credentials are printed into logs.

### 10. Regression verification

Confirm:

* Wisdom OS still builds.
* TypeScript checks pass.
* `GET /api/healthz` still returns:
  `{"status":"ok"}`
* Existing localStorage data remains untouched.
* No local-to-cloud migration has occurred.
* No existing task/project/category UI behavior was intentionally changed.
