We are continuing development of an existing Wisdom OS productivity app.

IMPORTANT:
This is a surgical architecture refactor, NOT a redesign and NOT a feature-expansion sprint.

Before changing anything:
1. Inspect the existing codebase.
2. Preserve all currently working functionality:
   - Today
   - Brain Dump
   - Daily Planning
   - Focus Mode
   - Review
   - task completion
   - daily plans
   - focus session history
3. Preserve the existing visual design and UX.
4. Do NOT add authentication.
5. Do NOT add a database.
6. Do NOT introduce a new UI framework.
7. Do NOT rewrite the application from scratch.
8. Do NOT remove existing functionality just to simplify the implementation.
9. Make the smallest clean architectural changes necessary.

The current application is a single-user localStorage prototype, but it currently contains hard-coded personal/example data. We need to separate the application engine from the user's data.

==================================================
GOAL
==================================================

Refactor Wisdom OS so that:

APPLICATION LOGIC
    ↓
USER/WORKSPACE DATA
    ↓
Tasks
Projects
Categories
Daily Plans
Focus Sessions

Instead of:

UI
    ↓
mockData.ts
    ↓
hard-coded personal projects/tasks/categories

The application must be capable of eventually supporting different users with different projects and categories without modifying the application code.

For now, localStorage remains the persistence layer.

==================================================
1. PROJECTS MUST BECOME REAL APPLICATION DATA
==================================================

Currently:
- src/mockData.ts contains projects.
- ProjectsScreen.tsx imports projects directly from mockData.
- OrganizeSheet.tsx imports projects directly from mockData.
- Projects are not stored in TaskContext.

Change this.

Create a proper project data model and make projects available through the application's state/data layer.

The Project model should at minimum contain:

id
name
description
createdAt
updatedAt

Add a sensible status field if useful for future archiving, such as:
status: 'ACTIVE' | 'ARCHIVED'

Do not over-engineer this.

Add project state and persistence to the existing context/storage architecture.

The UI should obtain projects through the application state layer rather than importing them from mockData.

Update:
- ProjectsScreen.tsx
- OrganizeSheet.tsx
- any other components that directly import projects from mockData

so they use the application's project state.

Existing project functionality must continue working.

2. CATEGORIES MUST BECOME DATA-DRIVEN
==================================================

Currently categories are hard-coded:

'MONEY'
'BUILD'
'LEARN'
'ADMIN'
'LATER'

and CATEGORY_LABELS is hard-coded in types.ts.

Refactor categories so they are represented as data.

Create a Category model containing at minimum:

id
name
createdAt
updatedAt

Optionally include a simple status field if needed.

Tasks should reference a category by categoryId rather than depending on a hard-coded TaskCategory union.

IMPORTANT:
Do NOT blindly delete the existing TaskCategory type if existing components still depend on it.

Perform a controlled migration.

Existing tasks using:

MONEY
BUILD
LEARN
ADMIN
LATER

must continue working after the refactor.

Create default starter categories corresponding to those five categories so the current workflow is preserved.

Their display names should initially be:

Money
Build
Learn
Admin
Later

Do NOT force these categories into application code permanently.

The goal is that categories can eventually be changed or customized by a user without changing TypeScript source code.

3. UPDATE ORGANIZE SHEET
==================================================

OrganizeSheet.tsx currently contains:

  'MONEY',
  'BUILD',
  'LEARN',
  'ADMIN',
  'LATER'
];

and imports CATEGORY_LABELS from types.ts.

Remove this hard-coded category list from the component.

OrganizeSheet should receive/read categories from the application state layer.

Preserve the existing UX and styling.

Preserve this behavior during migration.

Do not over-engineer a full rules engine.

==================================================
4. REMOVE PRODUCTION DEPENDENCY ON mockData
==================================================

mockData.ts currently contains:

- personal/example projects
- personal/example tasks

These must no longer be the default source of application data.

A brand-new workspace/user should NOT automatically receive personal example tasks such as:

"Build my first ecommerce automation workflow"

or:

"Reply to client messages"

Those are developer/sample data, not universal application data.

Convert mockData.ts into optional seed/demo data only.

For example, it may expose sample data through a function such as:

createSampleData()

but the application must not automatically use it as the fallback when localStorage is empty.

The existing TaskContext currently does:

loadTasks() ?? initialTasks

Change this behavior.

A new empty workspace should start with:
- no tasks
- starter categories
- no personal/example projects unless explicitly seeded

Do NOT remove the ability to use sample data for development/testing.
