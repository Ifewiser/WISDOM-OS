# 1. Supabase client

Add the minimum required Supabase client dependency/configuration.

The browser client must use only:

* Supabase project URL
* Supabase publishable/anon client key

Never expose:

* service_role key
* secret key
* database password
* privileged server credentials

Use environment variables.

Do not hard-code credentials.

If credentials are not available in the Replit environment, create clearly named placeholders/documentation and make the application fail gracefully rather than inventing values.

Do not implement:

* Google

* OTP
* SSO

Those can be future phases.

Use Supabase Auth as the source of truth for identity.

Do not create a custom users table.

The existing profiles table references:

auth.users(id)

# 3. Authentication UI

Add the minimum UI necessary for:

* Sign up

# 4. Profile bootstrap

After successful authentication:

Ensure a profile exists for the authenticated user.

Profile:

profiles.id = auth.users.id

Set:

display_name

timezone

created_at

updated_at

Timezone should initially be derived from the browser's IANA timezone when available.

For example:

Africa/Lagos

Do not hard-code Nigeria or any other timezone.

If the browser timezone cannot be determined, use UTC.

Profile creation must be safe to retry.

Do not create duplicate profiles.

---

# 5. First workspace bootstrap

After authentication, ensure the user has a workspace.

For the initial release:

ONE USER → ONE INITIAL WORKSPACE

Do not build multi-workspace UI yet.

The workspace should:

* be created with a generated UUID
* have a sensible default name
* use the user's detected timezone
* set created_by = authenticated user's ID

Then create:

workspace_members:
workspace_id = new workspace
user_id = authenticated user
role = owner

The bootstrap process must be idempotent.

Refreshing the browser must NOT create another workspace.

Signing out and back in must NOT create another workspace.

---

# 6. Starter categories

When the user's first workspace is created, create exactly these five starter categories:

Money
Build
Learn
Admin
Later

With system_key:

MONEY
BUILD
LEARN
ADMIN
LATER

They belong to the user's workspace.

Do NOT create global categories.

Do NOT use fixed UUIDs.

Do NOT infer Later behavior from the category name.

The system_key is authoritative.

If bootstrap is retried, do not duplicate categories.

---

# 7. Workspace membership model

The current application is single-user in product behavior, but the database must remain workspace-based.

For Phase 6C:

* creator becomes owner
* owner can access the workspace
* no invitation UI
* no member-management UI
* no collaboration features

Do not build unused complexity.

The workspace_members table is the security boundary.

---

# 8. RLS architecture

This is the most important part of this phase.

RLS must enforce authorization at the database level.

Never rely on frontend checks alone.

A user should only access workspace-owned data when:

auth.uid() is a member of that workspace.

Create a carefully designed helper function if useful, such as:

is_workspace_member(workspace_id)

IMPORTANT:

Avoid recursive RLS evaluation on workspace_members.

The helper must be implemented safely, preferably using SECURITY DEFINER where appropriate, with a locked-down search_path and no unsafe ability for callers to manipulate it.

Do not blindly copy a generic internet RLS function.

---

# 9. Profiles RLS

Authenticated users may:

SELECT their own profile.

INSERT their own profile.

UPDATE their own profile.

They must not be able to modify another user's profile.

They must not be able to delete another user's profile.

Keep policies based on:

auth.uid() = profiles.id

---

# 10. Workspaces RLS

Authenticated users may SELECT workspaces they belong to.

Only the workspace owner should be able to:

UPDATE workspace settings.

Only the owner should be able to DELETE the workspace.

Workspace creation must ensure:

created_by = auth.uid()

A user must never be able to create a workspace where another user is the creator.

---

# 11. workspace_members RLS

Users may SELECT membership records for workspaces they belong to.

For Phase 6C, membership management should be minimal.

The authenticated user should not be able to:

* promote themselves
* assign themselves owner/admin
* insert arbitrary membership records
* remove another owner

The bootstrap process must safely create the initial owner membership.

Do not expose an unrestricted INSERT policy merely to make signup easier.

Prefer a controlled bootstrap mechanism.

---

# 12. Bootstrap security

The profile/workspace/category bootstrap must be secure and idempotent.

Do not solve bootstrap by giving the browser unrestricted INSERT access to:

workspace_members

or unrestricted access to workspace ownership fields.

Possible approaches:

A. Authenticated database function/RPC with strict auth.uid() validation.

OR

B. Carefully constrained RLS policies that only permit creation of records where the authenticated user is the creator and membership owner.

Prefer the simplest secure approach.

Do not introduce a service-role key into frontend code.

If an RPC is used:

* validate auth.uid()
* create profile if missing
* create workspace if missing
* create owner membership
* create five starter categories
* return the workspace ID

Make the operation safe to call repeatedly.

---

# 13. Categories RLS

Workspace members can:

SELECT categories in their workspace.

For Phase 6C, members may:

INSERT
UPDATE

categories belonging to their workspace.

Deletion should remain restricted because the product uses ARCHIVED status.

The database must prevent changing:

system_key

for system categories through normal client updates.

The Later system behavior must remain stable.

---

# 14. Projects RLS

Workspace members may:

SELECT projects in their workspace.

INSERT projects into their workspace.

UPDATE projects in their workspace.

Deletion should not be broadly enabled because projects are archived.

The database must prevent cross-workspace project manipulation.

---

# 15. Tasks RLS

Workspace members may:

SELECT tasks in their workspace.

INSERT tasks where:

workspace_id belongs to a workspace they are a member of

created_by = auth.uid()

UPDATE tasks in their workspace.

Do not permit a user to insert a task into Workspace A while referencing a category/project from Workspace B.

The existing composite foreign keys must continue enforcing this.

Delete behavior should remain conservative.

Do not add broad task deletion unless required by the existing application.

---

# 16. Daily plans RLS

Daily plans are PERSONAL even though they belong to a workspace.

A user may access a daily plan only when:

workspace membership is valid

AND

daily_plans.user_id = auth.uid()

Therefore:

User A must not be able to read User B's daily plans.

User A must not be able to modify User B's daily plans.

For inserts:

user_id must equal auth.uid()

For updates/deletes:

user_id must equal auth.uid()

---

# 17. daily_plan_items RLS

Access should follow the parent daily plan.

A user may access plan items only when:

* the associated daily plan belongs to them
* the user is a member of the workspace

Prevent inserting an item into another user's daily plan.

Prevent inserting a task from another workspace.

The existing composite foreign keys remain the final database integrity layer.

---

# 18. Focus sessions RLS

Focus sessions are PERSONAL.

A user may:

SELECT their own focus sessions.

INSERT their own focus sessions.

UPDATE their own focus sessions.

They must not automatically see another user's focus history.

Require:

focus_sessions.user_id = auth.uid()

plus valid workspace membership.

Do not create workspace-wide focus analytics yet.

---

# 19. RLS security tests

Do NOT consider RLS complete because the UI appears correct.

Test actual database authorization.

Create at least two test users:

User A
User B

Create separate workspaces:

Workspace A
Workspace B

Verify:

### Workspace isolation

User A cannot SELECT Workspace B.

User B cannot SELECT Workspace A.

### Category isolation

User A cannot read, modify, or create categories in Workspace B.

### Project isolation

User A cannot read, modify, or create projects in Workspace B.

### Task isolation

User A cannot read, modify, or create tasks in Workspace B.

### Cross-workspace references

User A cannot create a task in Workspace A referencing:

* a category from Workspace B
* a project from Workspace B

### Daily-plan privacy

User A cannot read or modify User B's daily plan.

### Focus-session privacy

User A cannot read or modify User B's focus sessions.

### Membership escalation

User A cannot make themselves:

owner of Workspace B

or

admin of Workspace B.

### Workspace ownership

User A cannot change Workspace B's created_by.

### Profile isolation

User A cannot modify User B's profile.

Record actual database results, not merely frontend behavior.
