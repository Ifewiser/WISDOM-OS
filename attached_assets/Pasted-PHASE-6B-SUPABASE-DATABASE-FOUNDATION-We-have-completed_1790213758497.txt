PHASE 6B: SUPABASE DATABASE FOUNDATION

We have completed Phase 6A architecture audit.

The current Wisdom OS application is:

* React/Vite frontend
* TaskProvider as the main domain state layer
* localStorage persistence
* Express API currently only providing /api/healthz
* empty Drizzle/Postgres schema foundation
* no authentication
* no Supabase integration

Phase 5.5 smoke testing passed.

Now implement ONLY the database foundation.

DO NOT:

* implement authentication
* redesign the UI
* replace TaskContext
* remove localStorage
* implement local-to-cloud migration
* implement Supabase client integration
* add login/signup screens
* build collaboration UI
* build invitations/member management
* modify Focus Mode behavior
* modify Daily Planning behavior
* remove the existing Express health endpoint
* break existing localStorage functionality

The goal of this phase is to create a clean, secure Supabase/Postgres schema that Phase 6C can build on.

## 1. Database technology

Use Supabase Postgres.

Use PostgreSQL UUIDs for cloud entity IDs.

Use PostgreSQL `timestamptz` for timestamps.

Use PostgreSQL `date` for daily plan dates.

Use `gen_random_uuid()` for generated UUID primary keys.

Do not use local timestamp IDs as cloud primary keys.

## 2. Create these tables

Create:

1. profiles
2. workspaces
3. workspace_members
4. categories
5. projects
6. tasks
7. daily_plans
8. daily_plan_items
9. focus_sessions

Supabase's `auth.users` remains managed by Supabase. Do not recreate it.

### profiles

Columns:

* id uuid primary key references auth.users(id) on delete cascade
* display_name text
* timezone text not null default 'UTC'
* created_at timestamptz not null default now()
* updated_at timestamptz not null default now()

### workspaces

Columns:

* id uuid primary key default gen_random_uuid()
* name text not null
* created_by uuid not null references auth.users(id)
* timezone text not null default 'UTC'
* created_at timestamptz not null default now()
* updated_at timestamptz not null default now()

### workspace_members

Columns:

* workspace_id uuid not null references workspaces(id) on delete cascade
* user_id uuid not null references auth.users(id) on delete cascade
* role text not null default 'owner'
* joined_at timestamptz not null default now()
* updated_at timestamptz not null default now()

Primary key:

(workspace_id, user_id)

Allowed roles:

owner
admin
member

For the current product, only the owner role needs to be actively used. Do not build collaboration features yet.

### categories

Columns:

* id uuid primary key default gen_random_uuid()
* workspace_id uuid not null references workspaces(id) on delete cascade
* name text not null
* description text
* status text not null default 'ACTIVE'
* system_key text
* legacy_id text
* created_at timestamptz not null default now()
* updated_at timestamptz not null default now()

Allowed status:

ACTIVE
ARCHIVED

Allowed system_key:

MONEY
BUILD
LEARN
ADMIN
LATER
NULL

Add constraints/indexes for:

* case-insensitive unique category names within a workspace
* unique non-null system_key within a workspace
* workspace-scoped unique legacy_id when present

System categories must retain their system_key even if their display names are renamed.

### projects

Columns:

* id uuid primary key default gen_random_uuid()
* workspace_id uuid not null references workspaces(id) on delete cascade
* name text not null
* description text not null default ''
* status text not null default 'ACTIVE'
* legacy_id text
* created_at timestamptz not null default now()
* updated_at timestamptz not null default now()

Allowed status:

ACTIVE
ARCHIVED

Add:

* case-insensitive unique project names within a workspace
* workspace-scoped unique legacy_id when present

Projects are archived rather than hard-deleted while referenced by tasks.

### tasks

Columns:

* id uuid primary key default gen_random_uuid()
* workspace_id uuid not null references workspaces(id) on delete cascade
* created_by uuid not null references auth.users(id)
* title text not null
* category_id uuid nullable
* project_id uuid nullable
* status text not null default 'INBOX'
* priority text not null default 'NONE'
* next_action text not null default ''
* legacy_id text
* created_at timestamptz not null default now()
* updated_at timestamptz not null default now()
* completed_at timestamptz nullable

Allowed status:

INBOX
ACTIVE
COMPLETED

Allowed priority:

BIG_ROCK
SUPPORT
ADMIN
NONE

IMPORTANT:

Category and project relationships must be workspace-safe.

A task in workspace A must never be able to reference a category or project in workspace B.

Use composite foreign-key protection involving workspace_id where appropriate.

Do not rely solely on frontend validation.

### daily_plans

Columns:

* id uuid primary key default gen_random_uuid()
* workspace_id uuid not null references workspaces(id) on delete cascade
* user_id uuid not null references auth.users(id)
* plan_date date not null
* planning_completed boolean not null default false
* legacy_id text
* created_at timestamptz not null default now()
* updated_at timestamptz not null default now()

Unique:

(workspace_id, user_id, plan_date)

Daily plans are personal to the authenticated user even though they belong to a workspace.

### daily_plan_items

Create this as the normalized replacement for the local arrays.

Columns:

* workspace_id uuid not null
* daily_plan_id uuid not null references daily_plans(id) on delete cascade
* task_id uuid not null
* role text not null
* position smallint not null default 0
* created_at timestamptz not null default now()

Primary key:

(daily_plan_id, task_id)

Allowed role:

BIG_ROCK
SUPPORT
ADMIN

Ensure task and plan belong to the same workspace.

Prevent duplicate task membership in a plan.

Do not store:

* big_rock_task_id
* support_task_ids[]
* admin_task_ids[]

as PostgreSQL array columns.

IMPORTANT DOMAIN RULE:

daily_plan_items.role represents the task's historical role in that specific plan.

tasks.priority represents the task's current planning priority.

Do not collapse these into one concept.

Do not create an unnecessarily complicated trigger system to enforce every UI planning rule at this stage. Database integrity should prevent invalid relationships and duplicate membership, while application logic continues to enforce the current 1 Big Rock / max 2 Support UX.

### focus_sessions

Columns:

* id uuid primary key default gen_random_uuid()
* workspace_id uuid not null references workspaces(id) on delete cascade
* user_id uuid not null references auth.users(id)
* task_id uuid not null
* duration_seconds integer not null
* started_at timestamptz not null
* ended_at timestamptz nullable
* status text not null
* paused_remaining_seconds integer nullable
* legacy_id text
* created_at timestamptz not null default now()
* updated_at timestamptz not null default now()

Allowed status:

RUNNING
PAUSED
COMPLETED
ENDED

Constraints:

* duration_seconds > 0
* paused_remaining_seconds >= 0 when present
* ended_at >= started_at when present
* completed/ended sessions must have ended_at
* task must belong to the same workspace

Create a partial unique index so one user/workspace cannot have multiple RUNNING or PAUSED sessions simultaneously.

## 3. Foreign-key integrity

Where an entity belongs to a workspace and references another workspace entity, protect against cross-workspace references.

At minimum ensure:

tasks.workspace_id + tasks.category_id
-> categories.workspace_id + categories.id

tasks.workspace_id + tasks.project_id
-> projects.workspace_id + projects.id

daily_plan_items.workspace_id + daily_plan_items.task_id
-> tasks.workspace_id + tasks.id

focus_sessions.workspace_id + focus_sessions.task_id
-> tasks.workspace_id + tasks.id

daily_plan_items.workspace_id + daily_plan_items.daily_plan_id
-> daily_plans.workspace_id + daily_plans.id

Use PostgreSQL-compatible composite constraints correctly. If implementation requires additional unique constraints to support composite foreign keys, add only the necessary ones.

## 4. Indexes

Add the useful indexes identified in the architecture audit.

Priority:

* workspace_members(user_id, workspace_id)
* categories(workspace_id, status)
* projects(workspace_id, status)
* tasks(workspace_id, status, created_at DESC)
* tasks(workspace_id, project_id, status)
* tasks(workspace_id, category_id, status)
* daily_plan_items(daily_plan_id, role, position)
* daily_plan_items(workspace_id, task_id)
* focus_sessions(workspace_id, user_id, started_at DESC)
* focus_sessions(workspace_id, task_id, started_at DESC)

Also add the workspace-scoped unique legacy_id indexes required for migration idempotency.

Do not blindly index every column.

## 5. RLS

Enable Row Level Security on every application table.

However, authentication is NOT being implemented in this phase.

Create the schema so RLS can safely be implemented in Phase 6C.

Do not create unsafe policies that effectively make all rows public.

If helper functions are required for workspace membership, design them carefully so they do not create recursive RLS evaluation.

If it is cleaner to enable RLS now and leave policies to Phase 6C, do that.

Security is more important than making the tables immediately queryable.

## 6. Automatic updated_at

Implement a reusable PostgreSQL trigger/function for updating updated_at on UPDATE.

Do not duplicate separate trigger logic unnecessarily for every table.

## 7. Starter categories

Do NOT create global category rows.

Starter categories belong to a workspace.

Workspace bootstrap will happen in the authentication phase.

Therefore, this phase should create the schema only unless there is a safe schema-level seed mechanism that does not create orphan workspaces.

The five system categories remain:

MONEY
BUILD
LEARN
ADMIN
LATER

## 8. Legacy compatibility

Do not change existing localStorage code.

The database should contain nullable legacy_id fields needed for migration.

Do not migrate any local data yet.

## 9. Migration infrastructure

Do not implement migration logic yet.

Do ensure the schema supports deterministic migration through:

* workspace-scoped legacy IDs
* unique daily plan per user/workspace/date
* stable system_key values
* UUID cloud IDs
* foreign-key integrity

Do NOT create a giant migration RPC in this phase.

We will design migration separately after authentication is working.

## 10. Existing Drizzle package

Inspect the current `lib/db` implementation before choosing the schema location.

If the existing project already has a Drizzle migration workflow, integrate the new schema into it rather than creating a second competing migration system.

If the current Drizzle setup is incomplete, document that clearly rather than installing unnecessary tooling.

Do not remove the existing database package.

## 11. Environment variables

Do not add fake Supabase credentials.

Do not commit secrets.

If configuration placeholders are required, use clearly named environment variables without real values.

Never expose a Supabase service-role key in frontend code.
